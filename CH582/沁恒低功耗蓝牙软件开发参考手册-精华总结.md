# 沁恒低功耗蓝牙软件开发参考手册 - 重点总结

> 来源：`沁恒低功耗蓝牙软件开发参考手册 V1.9，2025-07-17`。本文件不是逐字摘录，而是按开发者阅读路径重组：看完应能掌握手册的整体脉络、主要开发模型、关键规范、常用 API 和常见约束。

## 0. 一句话总览

这份手册讲的是：在沁恒 CH58x 这类集成 BLE 的 RISC-V 单芯片上，如何基于 TMOS 事件调度模型、BLE 协议栈库、GAP/GATT/Profile 机制，开发 BLE 外围设备、中心设备以及简单 2.4GHz RF 应用。

核心主线如下：

```text
硬件 CH58x
  -> SDK 组件：TMOS / HAL / BLE Stack / Profiles / RISC-V Core / Application
  -> main 初始化：时钟、IO、UART、BLE 库、HAL、GAPRole、应用任务
  -> TMOS 主循环：任务注册、事件标志、定时事件、消息传递
  -> BLE 协议栈：GAP 管广播/扫描/连接/角色/绑定，GATT 管服务/特征/读写/通知
  -> 应用：配置参数、注册服务、注册回调，在事件和回调中实现业务逻辑
```

最需要牢牢记住的开发规范有四条：

1. `TMOS_SystemProcess()` 必须在 `main()` 的主循环中持续执行。
2. TMOS 是轮询式事件调度，不是多线程 RTOS；业务处理不能长时间阻塞。
3. BLE 对时序敏感，连接事件、广播事件前控制器必须及时处理；不要长期关闭全局中断，ISR 也不要过长。
4. 使用 TMOS 消息时，申请、发送、接收、处理、释放必须成对完成，避免内存泄漏。

## 1. 开发平台与软件包结构

### 1.1 CH58x 平台定位

CH58x 是集成 BLE 无线通信的 32 位 RISC-V MCU，片上包含 BLE 通信模块、USB、SPI、RTC、ADC、触摸按键、电源管理等外设。手册以 CH58x 为例，但同类沁恒低功耗蓝牙芯片的软件开发可参考同一套思路。

CH58x 是单芯片方案：Controller、Host、Profile、Application 都运行在同一芯片上。开发时通常参考 `Peripheral` 和 `Central` 例程。

### 1.2 SDK 六个主要组件

| 组件 | 作用 |
|---|---|
| TMOS | 任务与事件调度核心，负责事件、定时、消息和部分内存管理。 |
| HAL | 硬件抽象层，连接协议栈和芯片外设驱动。 |
| BLE Stack | BLE 协议栈库，通常以库文件形式提供，不开放全部源码。 |
| Profiles | GAP Role、GAP 安全、GATT Profile、GATT 服务等。 |
| RISC-V Core | 内核访问相关源码和头文件。 |
| Application | 用户应用层代码，例程的 `main()` 通常在此。 |

SDK 提供四类 GAP 角色配置文件：`Peripheralrole`、`Centralrole`、`Broadcasterrole`、`Observerrole`，并提供若干 GATT 配置文件和应用例程。

### 1.3 Peripheral 工程目录理解

| 目录 | 内容 |
|---|---|
| `APP` | 应用层源文件和头文件，含例程 `main()`。 |
| `HAL` | 硬件抽象层代码。 |
| `LIB` | BLE 协议栈库文件。 |
| `LD` | 链接脚本。 |
| `Profile` | GAP 角色、安全配置、GATT Profile、GATT 服务头文件。 |
| `RVMSIS` | RISC-V 内核访问文件。 |
| `Startup` | 启动文件。 |
| `StdPeriphDriver` | 芯片外设底层驱动。 |
| `obj` | 编译输出，例如 map、hex 等。 |

## 2. BLE 协议栈整体架构

BLE 协议栈由 `Host` 和 `Controller` 两大部分组成。CH58x 作为单芯片方案时，这两部分都在芯片内运行；应用通常不直接操作底层射频，而是通过 GAP、GATT、GAPRole、GATTServApp 等 API 使用协议栈。

### 2.1 分层关系

```text
Application
  -> GAP Role / Security Profile
  -> GATT Profiles
Host:
  -> GAP / GATT / ATT / SM / L2CAP
HCI:
  -> 单芯片场景下表现为函数调用和回调
Controller:
  -> Link Layer
  -> PHY
```

### 2.2 主要层职责

| 层 | 关键职责 |
|---|---|
| PHY | 2.4GHz 物理层，GFSK 调制；BLE 5.0 有 1M、2M、Coded PHY。 |
| Link Layer | 控制 Standby、Advertising、Scanning、Initiating、Connected 等链路状态。 |
| HCI | Host 和 Controller 之间的接口；本手册中主要表现为函数 API 与回调。 |
| L2CAP | 在上层协议和下层协议栈之间传输数据，支持分割重组、复用、连接类型等。 |
| SM | 安全管理，负责配对、密钥分发、安全连接和数据交换。 |
| ATT | 定义属性实体：UUID、句柄、属性值，以及读、写、通知等操作。 |
| GATT | 基于 ATT 定义服务和特征框架，应用数据主要通过 GATT 交换。 |
| GAP | 管理广播、扫描、连接、角色、安全绑定等对外可见行为。 |

### 2.3 BLE 角色概念

GAP 角色和 GATT 角色不是同一个维度。

| 维度 | 角色 | 含义 |
|---|---|---|
| GAP | Broadcaster | 只广播，不能连接。 |
| GAP | Observer | 只扫描广播，不能发起连接。 |
| GAP | Peripheral | 广播并可被连接，在链路层连接中通常作为从机。 |
| GAP | Central | 扫描并发起连接，在链路层连接中通常作为主机。 |
| GATT | Server | 提供属性表，供客户端读写。 |
| GATT | Client | 访问服务器的服务、特征和属性。 |

常见组合是：外设设备作为 GAP Peripheral + GATT Server，手机作为 GAP Central + GATT Client。但协议上并不强制绑定，Peripheral 也可以是 GATT Client，Central 也可以是 GATT Server。

## 3. TMOS：任务、事件、定时与消息

TMOS 是本手册的开发基础。BLE 协议栈、Profile、应用任务都围绕 TMOS 运行。

### 3.1 TMOS 的本质

TMOS 是以事件轮询为核心的任务管理机制，不是传统多线程操作系统。它的基本元素是：

```text
Task ID + Task Init + Event Handler + Event Flags
```

任务通过 `TMOS_ProcessEventRegister()` 注册事件处理回调，得到一个 8 位任务 ID。任务 ID 越小，优先级越高。协议栈任务必须具备最高优先级。

### 3.2 主循环规范

主程序最后必须循环执行：

```c
while (1) {
    TMOS_SystemProcess();
}
```

这不是可选项。没有持续执行 TMOS，协议栈事件、应用事件、定时器和消息都无法正常调度。

### 3.3 事件模型

每个任务的事件标志位是 16 位变量。规则如下：

| 规则 | 说明 |
|---|---|
| 每一位代表一个事件 | 同一任务内，一个 bit 对应一个事件。 |
| 用户最多自定义 15 个事件 | `0x8000` 被系统预留为 `SYS_EVENT_MSG`。 |
| 事件标志为 1 表示待执行 | 任务轮询到事件后调用对应处理逻辑。 |
| 事件处理后要清除标志 | 常见写法是 `return events ^ EVENT_NAME;`。 |
| TMOS tick 单位 | 一般来自 RTC，单位为 625 us。 |

立即触发事件用：

```c
tmos_set_event(taskID, EVENT_NAME);
```

延时触发一次事件用：

```c
tmos_start_task(taskID, EVENT_NAME, timeout);
```

周期事件通常在事件处理函数内部再次调用 `tmos_start_task()` 设置下一次触发。

### 3.4 事件处理代码习惯

事件处理的通用结构是：

```c
if (events & EVENT_NAME) {
    /* do something */
    return events ^ EVENT_NAME;
}
```

关键点不是代码形式，而是执行后必须清除当前事件位，否则会重复处理同一事件。

### 3.5 TMOS 消息传递

TMOS 支持任务间消息传递。典型流程如下：

```text
发送方：tmos_msg_allocate()
    -> 填充消息内容
    -> tmos_msg_send(targetTaskID, msg)
    -> 目标任务 SYS_EVENT_MSG 置位

接收方：在 SYS_EVENT_MSG 中 tmos_msg_receive()
    -> 根据消息头 event 分发处理
    -> tmos_msg_deallocate()
```

规范要点：

| 事项 | 规范 |
|---|---|
| 申请内存 | 用 `tmos_msg_allocate(len)`，失败返回 `NULL`。 |
| 发送消息 | 用 `tmos_msg_send(taskID, msg_ptr)`。 |
| 接收消息 | 在 `SYS_EVENT_MSG` 中调用 `tmos_msg_receive(taskID)`。 |
| 释放消息 | 处理完成后必须 `tmos_msg_deallocate(pMsg)`。 |
| 消息类型 | 通过消息头部的 `event` 字段区分，例如 `KEY_CHANGE`、`GATT_MSG_EVENT`。 |

### 3.6 TMOS 内存与低功耗

TMOS 单独使用一块内存，用户可配置地址和大小。BLE 协议栈也使用此内存，因此需要在最大预期负载下测试，包括绑定、加密、多连接、通知、长数据等场景。

当任务执行完且无待处理事件时，系统会进入空闲或睡眠模式。应用若占用过长，会影响 BLE 控制器时序，严重时导致重传或断连。

## 4. main 初始化路径与应用结构

Peripheral 例程展示了典型 BLE 从机应用的初始化路径。

### 4.1 main 的基本执行顺序

```text
1. 可选启用 DCDC
2. 设置系统时钟，例如 PLL 60MHz
3. 配置 GPIO 输入上拉，避免 IO 浮空导致电流不稳定
4. DEBUG 模式下初始化 UART 打印
5. 打印 BLE 库版本
6. CH58X_BLEInit() 初始化 BLE 库
7. HAL_Init() 初始化 HAL 层
8. GAPRole_PeripheralInit() 初始化 GAP Peripheral 角色任务
9. Peripheral_Init() 初始化应用任务、参数、服务、回调
10. while(1) 中运行 TMOS_SystemProcess()
```

### 4.2 BLE 库初始化

`CH58X_BLEInit()` 负责通过 `bleConfig_t` 配置 BLE 库参数，例如内存、时钟、发射功率等，然后调用库初始化接口。

### 4.3 HAL 初始化

`HAL_Init()` 主要做三类工作：

1. 注册 HAL 任务，例如 `halTaskID = TMOS_ProcessEventRegister(HAL_ProcessEvent)`。
2. 初始化硬件相关功能，例如 RTC、睡眠唤醒、LED、按键等。
3. 根据配置启动 RF 校准或测试事件。

### 4.4 Peripheral 应用初始化

低功耗蓝牙从机初始化由两部分组成：

1. GAP 角色初始化，由 BLE 库完成，例如 `GAPRole_PeripheralInit()`。
2. 应用初始化，由用户工程完成，包括：
   - 注册应用任务。
   - 配置广播参数、连接参数、绑定参数。
   - 注册 GATT 服务。
   - 注册 GAPRole、GATT Profile、BondMgr 回调。

### 4.5 应用代码放在哪里

应用逻辑通常写在两个位置：

| 位置 | 适合内容 |
|---|---|
| TMOS 事件处理函数 | 周期任务、状态机推进、异步任务拆分。 |
| 回调函数 | BLE 状态变化、特征值变化、连接参数更新、RSSI、GATT 消息等。 |

例如周期任务由 `SBP_PERIODIC_EVT` 触发，默认周期可为 5000 ms，处理完成后重新启动下一次定时事件。

## 5. GAP：广播、扫描、连接与连接参数

GAP 是 BLE 设备行为的对外接口层，主要处理设备发现、广播、连接、绑定和安全。

### 5.1 GAP 状态

| 状态 | 含义 |
|---|---|
| Standby | 协议栈未启用或空闲。 |
| Advertiser | 设备广播数据，广播中可包含名称、地址、服务等信息。 |
| Scanner | 扫描广播包，可发送扫描请求并读取扫描响应。 |
| Initiator | 发起连接，指定目标地址并初始化连接参数。 |
| Master / Slave | 建连后角色。广播者通常成为 Slave，发起者通常成为 Master。 |

### 5.2 连接参数

| 参数 | 单位/范围 | 作用 |
|---|---|---|
| Connection Interval | 单位 1.25 ms，范围 7.5 ms - 4 s | 两个连接事件之间的时间。越短响应越快、吞吐越高，但功耗越大。 |
| Slave Latency | 范围 0 - 499 | 从机可跳过的最大连接事件数。无数据时可降低从机功耗。 |
| Supervision Timeout | 单位 10 ms，范围约 100 ms - 32 s | 两个有效连接事件之间允许的最大时间，超过则判定断连。 |

有效连接间隔：

```text
有效连接间隔 = 连接间隔 × (1 + 从设备延迟)
```

例如连接间隔为 100 ms、从设备延迟为 4，则无数据传输时从机约每 500 ms 参与一次连接事件。

### 5.3 参数取舍

| 调整 | 结果 |
|---|---|
| 减小连接间隔 | 功耗上升，吞吐上升，往返延迟下降。 |
| 增大连接间隔 | 功耗下降，吞吐下降，往返延迟上升。 |
| 减小 Slave Latency | 从机功耗上升，主机给从机发数据的等待时间下降。 |
| 增大 Slave Latency | 从机无数据时功耗下降，但主机给从机发数据的等待时间上升。 |

设计连接参数时必须同时满足：监督超时大于有效连接间隔，且有效连接间隔不能过长，否则连接稳定性和响应都会变差。

### 5.4 连接参数更新

从机可向主机发送连接参数更新请求，包含：最小连接间隔、最大连接间隔、从设备延迟、监督超时。主机可以接受，也可以拒绝。

手册中特别区分：

| API | 含义 |
|---|---|
| `GAPRole_PeripheralConnParamUpdateReq()` | 从机向主机协商连接参数。 |
| `GAPRole_UpdateLink()` | 主机直接配置连接参数。 |

### 5.5 常用 GAP 参数

| 参数 ID | 含义 |
|---|---|
| `TGAP_GEN_DISC_ADV_MIN` | 通用广播模式广播时长，单位 0.625 ms。 |
| `TGAP_LIM_ADV_TIMEOUT` | 限时可发现广播时长，单位 1 s。 |
| `TGAP_DISC_ADV_INT_MIN/MAX` | 广播最小/最大间隔，单位 0.625 ms。 |
| `TGAP_DISC_SCAN` | 扫描时长，单位 0.625 ms。 |
| `TGAP_DISC_SCAN_INT` | 扫描间隔，单位 0.625 ms。 |
| `TGAP_DISC_SCAN_WIND` | 扫描窗口，单位 0.625 ms。 |
| `TGAP_CONN_EST_SCAN_INT/WIND` | 建立连接时的扫描间隔/窗口。 |
| `TGAP_CONN_EST_INT_MIN/MAX` | 建立连接时的最小/最大连接间隔，单位 1.25 ms。 |
| `TGAP_CONN_EST_SUPERV_TIMEOUT` | 建立连接时的监督超时，单位 10 ms。 |
| `TGAP_CONN_EST_LATENCY` | 建立连接时的从设备延迟。 |

## 6. GAPRole：Peripheral 与 Central 开发模型

GAPRole 是封装 GAP 角色行为的任务，大部分代码在 BLE 库中运行，应用通过参数和回调与它交互。

### 6.1 四类 GAPRole

| 角色 | 能力 |
|---|---|
| Broadcaster | 只广播，不可连接。 |
| Observer | 只扫描，不可连接。 |
| Peripheral | 可广播，可作为从机被连接。 |
| Central | 可扫描，可作为主机发起单个或多个连接。 |

### 6.2 Peripheral 初始化流程

```text
1. 配置 GAPRole 参数
   - 是否启用广播
   - 广播数据
   - 扫描响应数据
   - 最小/最大连接间隔

2. 设置 GAP 特征
   - 例如设备名 GGS_DEVICE_NAME_ATT

3. 设置广播间隔
   - GAP_SetParamValue(TGAP_DISC_ADV_INT_MIN/MAX, advInt)

4. 启动设备
   - GAPRole_PeripheralStartDevice(taskID, bondCallbacks, roleCallbacks)

5. 在应用中处理回调
   - 广播状态
   - 已连接/断开
   - RSSI
   - 参数更新
```

### 6.3 Peripheral 常用状态回调

| 状态 | 含义 |
|---|---|
| `GAPROLE_INIT` | 等待启动。 |
| `GAPROLE_STARTED` | 初始化完成但未广播。 |
| `GAPROLE_ADVERTISING` | 正在广播。 |
| `GAPROLE_WAITING` | 已启动但未广播，等待再次广播。 |
| `GAPROLE_CONNECTED` | 已连接。 |
| `GAPROLE_CONNECTED_ADV` | 已连接且仍在广播。 |
| `GAPROLE_ERROR` | 无效状态，表示错误。 |

### 6.4 Central 初始化流程

```text
1. 配置扫描结果数等 Central 参数
2. 调用 GAPRole_CentralStartDevice() 启动中心设备
3. 调用 GAPRole_CentralStartDiscovery() 开始扫描
4. 在 GAP_DEVICE_INFO_EVENT / GAP_DEVICE_DISCOVERY_EVENT 中解析设备
5. 调用 GAPRole_CentralEstablishLink() 建立连接
6. 建连后执行 GATT 服务发现、特征发现、读写等流程
```

### 6.5 GAPRole 常用 API

| API | 作用 |
|---|---|
| `GAPRole_SetParameter()` | 设置 GAP 角色参数。 |
| `GAPRole_GetParameter()` | 获取 GAP 角色参数。 |
| `GAPRole_TerminateLink()` | 断开指定连接。 |
| `GAPRole_ReadRssiCmd()` | 读取指定连接 RSSI。 |
| `GAPRole_PeripheralInit()` | 初始化从机 GAPRole 任务。 |
| `GAPRole_PeripheralStartDevice()` | 以从机角色启动设备。 |
| `GAPRole_PeripheralConnParamUpdateReq()` | 从机请求更新连接参数。 |
| `GAPRole_CentralInit()` | 初始化主机 GAPRole 任务。 |
| `GAPRole_CentralStartDevice()` | 以主机角色启动设备。 |
| `GAPRole_CentralStartDiscovery()` | 配置并启动扫描。 |
| `GAPRole_CentralCancelDiscovery()` | 停止扫描。 |
| `GAPRole_CentralEstablishLink()` | 与对端建立连接。 |

## 7. GAP 绑定与安全管理

GAPBondMgr 管理 BLE 连接中的安全事务，使某些数据只能在配对、加密、认证后读写。

### 7.1 安全术语

| 术语 | 含义 |
|---|---|
| Pairing 配对 | 交换密钥的过程。 |
| Encryption 加密 | 配对后使用密钥加密链路，或重新加密。 |
| Authentication 验证 | 配对过程带 MITM 保护。 |
| Bonding 绑定 | 将密钥保存到非易失性存储器，便于下次连接加密。 |
| Authorization 授权 | 在身份验证外增加应用级密钥交换。 |
| OOB | 密钥通过串口、NFC 等非无线方式交换，可提供 MITM 保护。 |
| MITM | 中间人保护，防止监听者通过无线传输破解密钥。 |
| Just Works | 无 MITM 的直接配对方式。 |

### 7.2 建立安全连接的一般流程

```text
1. 配对：Just Works 或 MITM
2. 使用密钥加密连接
3. 如启用绑定，将密钥保存到非易失性存储
4. 下次连接时使用保存的密钥加密连接
```

### 7.3 常见配置模式

| 模式 | 关键配置 |
|---|---|
| 关闭配对 | `GAPBOND_PAIRING_MODE_NO_PAIRING`，协议栈拒绝配对尝试。 |
| 直接配对但不绑定 | 允许配对，`MITM = FALSE`，`bonding = FALSE`。 |
| MITM 配对并绑定 | 设置 6 位 passkey，`MITM = TRUE`，`bonding = TRUE`，配置 IO 能力。 |

重要注意事项：IO 能力必须与硬件真实能力一致。例如设备没有键盘输入能力，就不能配置成需要在设备端输入密码，否则配对无法完成。

### 7.4 GAPBondMgr 常用 API 与参数

| API/参数 | 作用 |
|---|---|
| `GAPBondMgr_SetParameter()` | 设置绑定管理参数。 |
| `GAPBondMgr_GetParameter()` | 获取绑定管理参数。 |
| `GAPBondMgr_PasscodeRsp()` | 响应密码请求。 |
| `GAPBOND_PERI_PAIRING_MODE` | 外设配对方式。 |
| `GAPBOND_PERI_DEFAULT_PASSCODE` | 默认 MITM passkey，范围 0 - 999999。 |
| `GAPBOND_PERI_MITM_PROTECTION` | 是否启用 MITM。 |
| `GAPBOND_PERI_IO_CAPABILITIES` | 设备 IO 能力，例如 `DISPLAY_ONLY`。 |
| `GAPBOND_PERI_BONDING_ENABLED` | 是否在配对过程中请求绑定。 |

## 8. GATT：服务、特征、属性表与读写通知

GATT 是应用数据通信的核心。应用数据以服务、特征和属性形式组织。

### 8.1 GATT Server 与 Client

| 角色 | 含义 |
|---|---|
| GATT Server | 持有属性表，提供服务和特征，允许客户端读取、写入、订阅通知。 |
| GATT Client | 发现服务和特征，读取或写入服务器数据，接收通知或指示。 |

### 8.2 特征由哪些属性组成

典型 Characteristic 包含：

| 属性 | 作用 |
|---|---|
| Characteristic Declaration | 声明特征值的位置、类型和属性。 |
| Characteristic Value | 实际数据值。 |
| Client Characteristic Configuration，CCC | 客户端配置通知或指示。 |
| Characteristic User Description | 描述特征含义的 ASCII 字符串。 |

### 8.3 GATT 属性结构

每个属性包含：

| 字段 | 说明 |
|---|---|
| `type` | 属性类型，即 UUID，可为 2 字节或 16 字节。 |
| `permissions` | 访问权限，例如可读、可写、需认证、需加密。 |
| `handle` | GATTServApp 自动分配的句柄。 |
| `pValue` | 指向属性值的指针；初始化后长度不能改变；最大 512 字节。 |

常见权限：

| 权限 | 含义 |
|---|---|
| `GATT_PERMIT_READ` | 可读。 |
| `GATT_PERMIT_WRITE` | 可写。 |
| `GATT_PERMIT_AUTHEN_READ/WRITE` | 需身份验证后读/写。 |
| `GATT_PERMIT_AUTHOR_READ` | 需授权后读。 |
| `GATT_PERMIT_ENCRYPT_READ/WRITE` | 需加密后读/写。 |

### 8.4 SimpleProfile 示例

Peripheral 例程中的 `gattprofile` 是测试和演示用 GATT Profile，包含五个特征：

| 特征 | 能力 |
|---|---|
| `simpleProfilechar1` | GATT Client 可读写 1 字节。 |
| `simpleProfilechar2` | GATT Client 可读 1 字节，不能写。 |
| `simpleProfilechar3` | GATT Client 可写 1 字节，不能读。 |
| `simpleProfilechar4` | 可配置为向 Client 通知 1 字节，不能读写。 |
| `simpleProfilechar5` | GATT Client 可读 5 字节，不能写。 |

常见 Characteristic Properties：

| 值 | 含义 |
|---|---|
| `0x02` | 允许读取特征值。 |
| `0x04` | 允许无响应写入。 |
| `0x08` | 允许带响应写入。 |
| `0x10` | 允许通知，无确认。 |
| `0x20` | 允许指示，带确认。 |

### 8.5 GATT Server / GATTServApp 开发流程

GATT Server 多数功能通过 GATTServApp 配置。

```text
1. 定义固定大小的属性表 simpleProfileAttrTbl[]
2. 定义服务 UUID、特征声明、特征值、用户描述、CCC
3. 初始化 CCC：GATTServApp_InitCharCfg()
4. 注册服务：GATTServApp_RegisterService()
5. 注册应用回调：SimpleProfile_RegisterAppCBs()
6. 在读/写回调中校验权限、长度、偏移和参数
7. 应用通过 SimpleProfile_SetParameter() 等接口更新特征值
8. 需要通知时，检查 CCC 后发送 Notification 或 Indication
```

必须注意：属性值的长度初始化后不能随意改变；如果需要变长数据，应设计最大长度、长度字段或分片协议。

### 8.6 GATT Client 开发流程

GATT Client 不持有属性表，主要通过 API 访问 Server。

```text
1. GATT_InitClient()
2. GATT_RegisterForInd(taskID)，接收 ATT Indication / Notification
3. 建连后进行服务发现、特征发现、描述符发现
4. 已知 handle 后执行 Read / Write / WriteNoRsp 等操作
5. 在 TMOS 的 GATT_MSG_EVENT 中处理 ATT 响应
6. 处理完消息后释放 TMOS 消息内存
```

### 8.7 Notification 与 Indication

| 方式 | 是否需要确认 | 适用场景 |
|---|---|---|
| Notification | 不需要 ATT 层确认 | 高频、允许少量丢失或上层自校验的数据。 |
| Indication | 需要 ATT 层确认 | 重要状态、必须确认到达的数据。 |

手册特别提示：如果 `GATT_Notification()` 或 `GATT_Indication()` 返回失败，需要释放相关内存，避免泄漏。

### 8.8 GATT 常用 API

| API | 角色 | 作用 |
|---|---|---|
| `GATT_Indication()` | Server | 向 Client 指示特征值，要求确认。 |
| `GATT_Notification()` | Server | 向 Client 通知特征值，不要求确认。 |
| `GATT_ExchangeMTU()` | Client | 协商 ATT MTU。 |
| `GATT_DiscAllPrimaryServices()` | Client | 发现所有主服务。 |
| `GATT_DiscPrimaryServiceByUUID()` | Client | 按 UUID 发现主服务。 |
| `GATT_FindIncludedServices()` | Client | 查找包含服务。 |
| `GATT_DiscAllChars()` | Client | 在服务句柄范围内发现所有特征。 |
| `GATT_DiscCharsByUUID()` | Client | 按 UUID 发现特征。 |
| `GATT_DiscAllCharDescs()` | Client | 发现特征描述符。 |
| `GATT_ReadCharValue()` | Client | 按 handle 读取特征值。 |
| `GATT_ReadUsingCharUUID()` | Client | 按 UUID 读取特征值。 |
| `GATT_ReadLongCharValue()` | Client | 读取长特征值。 |
| `GATT_ReadMultiCharValues()` | Client | 读取多个特征值。 |
| `GATT_WriteNoRsp()` | Client | 无响应写入。 |
| `GATT_SignedWriteNoRsp()` | Client | 签名无响应写入，依赖认证/绑定条件。 |
| `GATT_WriteCharValue()` | Client | 带响应写入特征值。 |
| `GATT_WriteLongCharDesc()` | Client | 写入长特征/描述符数据。 |

### 8.9 GATTServApp 常用 API

| API | 作用 |
|---|---|
| `GATTServApp_InitCharCfg()` | 初始化客户端特征配置表。 |
| `GATTServApp_ReadCharCfg()` | 读取客户端特征配置。 |
| `GATTServApp_WriteCharCfg()` | 写入客户端特征配置。 |
| `GATTServApp_ProcessCCCWriteReq()` | 处理客户端对 CCC 的写请求。 |
| `GATTServApp_AddService()` | 添加协议栈必要 GATT 属性服务。 |
| `GATTServApp_RegisterService()` | 将自定义 Profile 属性表注册到 GATTServApp。 |

### 8.10 GATT 返回值与错误码

常见 GATT 返回：

| 返回值 | 含义 |
|---|---|
| `SUCCESS` | 指令执行成功。 |
| `INVALIDPARAMETER` | 连接句柄或请求字段无效。 |
| `MSG_BUFFER_NOT_AVAIL` | HCI 缓冲区不可用，应稍后重试。 |
| `bleNotConnected` | 设备未连接。 |
| `blePending` | 有 GATT 子过程或确认仍在进行。 |
| `bleTimeout` | 上一个事务超时。 |
| `bleMemAllocError` | 内存分配错误。 |
| `bleLinkEncrypted` | 链路已加密，不应发送带认证签名的 PDU。 |

常见 ATT 错误：

| 错误码 | 含义 |
|---|---|
| `ATT_ERR_INVALID_HANDLE` | 属性句柄无效。 |
| `ATT_ERR_READ_NOT_PERMITTED` | 不允许读。 |
| `ATT_ERR_WRITE_NOT_PERMITTED` | 不允许写。 |
| `ATT_ERR_INSUFFICIENT_AUTHEN` | 需要身份验证。 |
| `ATT_ERR_INSUFFICIENT_AUTHOR` | 需要授权。 |
| `ATT_ERR_INSUFFICIENT_ENCRYPT` | 需要加密。 |
| `ATT_ERR_ATTR_NOT_FOUND` | 句柄范围内找不到属性。 |
| `ATT_ERR_INVALID_VALUE_SIZE` | 属性值长度不适合当前操作。 |
| `ATT_ERR_INSUFFICIENT_RESOURCES` | 资源不足。 |

## 9. L2CAP 与 HCI

### 9.1 L2CAP

L2CAP 位于 HCI 上方，在 Host 的上层协议和下层协议栈之间传输数据。它提供：

- 分割和重组，使上层可处理更大的数据包。
- 协议复用，支持多种连接和连接类型。
- 服务质量和成组通信能力。

手册指出 CH58x BLE 协议栈支持有效最大 MTU 为 247。

### 9.2 HCI

HCI 连接 Host 与 Controller，将 Host 操作转成 Controller 指令。BLE Core Spec 支持 UART、USB、SDIO、3-Wire UART 等 HCI 类型。

但对 CH58x 这类全协议栈单芯片，本手册讨论的 HCI 主要是函数调用和函数回调，而不是外部 UART HCI 控制器模式。

## 10. 创建 BLE 应用程序的实际步骤

创建 BLE 应用时可按以下清单推进。

### 10.1 选择角色

先确定设备角色：`Central`、`Peripheral`、`Broadcaster`、`Observer`。不同角色调用不同的初始化 API。

### 10.2 配置 BLE 行为

根据业务定义：

- 广播数据和扫描响应数据。
- 广播间隔、扫描间隔、扫描窗口。
- 最小/最大连接间隔、Slave Latency、监督超时。
- 安全模式、配对方式、是否绑定。
- GATT 服务、特征、权限、通知/指示能力。

### 10.3 定义应用任务

应用必须包含：

- TMOS 任务注册。
- TMOS 事件处理函数。
- 协议栈回调函数。
- GATT Profile 回调函数。
- 消息处理分发函数。

### 10.4 配置 `config.h`

常见配置包括：

- DCDC 是否使能。
- RTC 时钟。
- 睡眠功能。
- MAC 地址。
- BLE 协议栈使用的 RAM 大小。
- `WAKE_UP_RTC_MAX_TIME`，即等待 32M 晶体稳定的时间。

`WAKE_UP_RTC_MAX_TIME` 受晶体、电压、环境稳定性等影响，应给唤醒时间留缓冲，提升系统稳定性。

### 10.5 BLE 工作期间的应用限制

BLE 协议时序敏感。控制器必须在每个连接事件或广播事件到来前完成必要处理。如果应用任务长时间占用 CPU，可能导致重传或断连。

规范：复杂业务应拆成多个 TMOS 事件分段执行，不要在单个事件中做大块阻塞计算、长时间打印、长循环等待或同步 IO。

### 10.6 中断限制

BLE 工作期间，RTC 定时器用于时间计算。不要长时间禁止全局中断；单个 ISR 也不宜耗时过长，否则会长期打断 BLE 工作并导致连接断开。

## 11. 创建简单 RF 应用程序

RF 应用基于 RF PHY 直接实现 2.4GHz 通信，不建立 BLE 协议。因此它适合自定义私有 2.4GHz 通信，而不是标准 BLE 手机互联。

### 11.1 RF 初始化流程

```text
1. CH58X_BLEInit()
2. RF_RoleInit()
3. 注册 RF 应用任务：TMOS_ProcessEventRegister(RF_ProcessEvent)
4. 填充 rfConfig_t
5. RF_Config(&rfConfig)
6. 使用 RF_Rx() / RF_Tx() 收发
7. 在 RF_2G4StatusCallBack() 中接收状态，再通过事件继续处理
```

### 11.2 RF 配置重点

| 字段 | 含义 |
|---|---|
| `LLEMode` | RF 模式，例如 Basic、Auto、指定频点、不带 RSSI 等。 |
| `Channel` | RF 通信通道，0 - 39。 |
| `Frequency` | RF 通信频率，2400000 KHz - 2483500 KHz。 |
| `AccessAddress` | RF 通信地址；不建议使用 `0x55555555`、`0xAAAAAAAA`，并避免过多位翻转或过长连续 0/1。 |
| `CRCInit` | CRC 初始值。 |
| `RFStatusCB` | RF 状态回调函数。 |
| `ChannelMap` | 频道图，每一位对应一个频道。 |
| `HeartPeriod` | 心跳包间隔，100 ms 的整数倍。 |
| `HopPeriod` | 跳跃周期。 |
| `HopIndex` | 跳频信道间隔值。 |
| `RxMaxlen` | RF 接收最大数据长度，默认 251。 |
| `TxMaxlen` | RF 发送最大数据长度，默认 251。 |

### 11.3 Basic 与 Auto 模式

| 模式 | 特点 |
|---|---|
| Basic | 基础单向发送/接收；发送方无法知道接收方是否成功收到。 |
| Auto | 在 Basic 基础上增加响应机制；接收方收到后返回数据，发送方自动切到接收模式等待响应。 |

Auto 模式下，RF 发送完成后自动进入接收模式，超时时间为 3 ms；若 3 ms 内无响应则关闭接收。接收数据和超时状态均通过回调返回应用层。

### 11.4 自动跳频

RF Auto 模式支持自动跳频，用于缓解 2.4GHz 信道干扰。使用方法：

```text
发送方：启动跳频发送事件 -> RF_FrequencyHoppingTx(resendCount)
接收方：启动跳频接收事件 -> RF_FrequencyHoppingRx(timeoutMS)
```

注意：如果接收方已经处于接收模式，需要先调用 `RF_Shut()` 关闭 RF，再开启跳频接收事件。

### 11.5 RF PHY 常用 API

| API | 作用 |
|---|---|
| `RF_RoleInit()` | 初始化 RF 协议栈角色。 |
| `RF_Config()` | 配置 RF 参数。 |
| `RF_Rx()` | 配置为接收状态；收到数据后需要重新配置。 |
| `RF_Tx()` | 发送 RF 数据。 |
| `RF_Shut()` | 关闭 RF，停止发送或接收。 |
| `RF_FrequencyHoppingTx()` | 发送端开启跳频。 |
| `RF_FrequencyHoppingRx()` | 接收端开启跳频。 |
| `RF_FrequencyHoppingShut()` | 关闭 RF 跳频。 |
| `RF_2G4StatusCallBack()` | RF 状态回调，收发完成均会进入。 |

RF 回调规范：不要在 `RF_2G4StatusCallBack()` 中直接调用 RF 接收或发送 API，应通过 TMOS 事件方式调用。

## 13. 开发规范与易错点清单

### 13.1 TMOS 相关

- 必须持续调用 `TMOS_SystemProcess()`。
- 每个任务最多 15 个用户事件，`SYS_EVENT_MSG` 不可复用。
- 事件处理结束必须清除事件位。
- 周期任务可在事件内重新 `tmos_start_task()`。
- 消息处理完成必须释放内存。
- 长任务要拆分，不要阻塞 BLE 事务。
- TMOS 不是多线程；不要按抢占式 RTOS 思路写业务。

### 13.2 低功耗与稳定性

- IO 初始化时避免浮空，否则电流可能不稳定。
- `config.h` 中的睡眠、RTC、DCDC、BLE RAM 配置要结合硬件验证。
- `WAKE_UP_RTC_MAX_TIME` 要留晶振稳定裕量。
- ISR 要短，不要长期关闭全局中断。
- 开启绑定、加密、通知、多连接等高负载场景后，要重新评估 TMOS 内存。

### 13.3 GAP 与连接参数

- 小连接间隔换低延迟和高吞吐，但功耗更高。
- 大连接间隔和高 Slave Latency 可降功耗，但上行/下行响应变慢。
- 监督超时必须大于有效连接间隔。
- 从机请求参数更新，主机可能拒绝。
- 连接断开后需要根据 GAPRole 状态决定是否重新广播或重连。

### 13.4 安全绑定

- 是否配对、是否绑定、是否 MITM，应与业务安全等级一致。
- IO 能力必须与硬件能力一致。
- 使用 MITM 时 passkey 范围为 0 - 999999。
- 需要加密或认证的 GATT 特征，应在属性权限中体现。

### 13.5 GATT 设计

- 先设计服务 UUID、特征 UUID、权限、长度、通知/指示策略。
- 属性值初始化后长度不可随意改变。
- CCC 必须初始化并正确处理写入。
- 通知前应确认客户端已启用 CCC。
- Notification 无确认，Indication 有确认，不能混用语义。
- GATT Client 读写响应通过 `GATT_MSG_EVENT` 到达应用层，处理后必须释放消息。

### 13.6 RF 应用

- RF 应用不等于 BLE 应用，手机 BLE 工具通常不能直接识别私有 RF 协议。
- Auto 模式有接收响应机制，Basic 模式没有确认机制。
- 回调中不要直接继续收发，应转成 TMOS 事件。
- 跳频接收前若 RF 已在接收状态，应先 `RF_Shut()`。

## 14. 四个典型开发流程

### 14.1 BLE Peripheral + GATT Server

```text
CH58X_BLEInit()
HAL_Init()
GAPRole_PeripheralInit()
Peripheral_Init()
  -> 注册应用任务
  -> 配置广播、扫描响应、连接参数
  -> 配置绑定参数
  -> GGS_AddService()
  -> GATTServApp_AddService()
  -> DevInfo_AddService()
  -> SimpleProfile_AddService()
  -> 注册 SimpleProfile 回调
  -> 启动 GAPRole_PeripheralStartDevice()
while(1) TMOS_SystemProcess()
```

### 14.2 BLE Central + GATT Client

```text
CH58X_BLEInit()
HAL_Init()
GAPRole_CentralInit()
Central_Init()
  -> GATT_InitClient()
  -> GATT_RegisterForInd(taskID)
  -> GAPRole_CentralStartDevice()
  -> GAPRole_CentralStartDiscovery()
扫描到目标设备
  -> GAPRole_CentralEstablishLink()
建连成功
  -> 发现服务/特征/描述符
  -> Read / Write / WriteNoRsp
  -> 在 GATT_MSG_EVENT 中处理响应
```

### 14.3 GATT Server 发送通知

```text
1. 定义支持 Notify 的特征
2. 添加 CCC 描述符
3. GATTServApp_InitCharCfg()
4. 客户端写 CCC 启用通知
5. 应用更新特征值
6. 调用 GATT_Notification()
7. 若返回失败，释放已申请内存
```

### 14.4 RF Auto 通信

```text
发送端：
  CH58X_BLEInit()
  RF_RoleInit()
  RF_Config(AUTO 模式)
  RF_Tx(data)
  自动切到 RX 等待响应，超时约 3 ms
  回调返回响应或超时

接收端：
  CH58X_BLEInit()
  RF_RoleInit()
  RF_Config(AUTO 模式)
  RF_Rx(responseData)
  收到数据后自动返回响应
  回调通知应用层
```

## 16. 最小知识闭环

如果只保留这份手册 70% 的关键知识，可以压缩成以下闭环：

```text
CH58x BLE 开发 = 单芯片 BLE Stack + TMOS 事件模型 + GAP 行为控制 + GATT 数据模型。

先初始化硬件和 BLE 库，再注册 TMOS 任务，配置 GAPRole，注册 GATT 服务和回调。
应用不应阻塞 TMOS；BLE 事件、GATT 消息、连接状态变化都通过事件或回调进入应用。
GAP 解决“如何发现、连接、安全绑定”；GATT 解决“连接后读写什么数据”。
低功耗和稳定性主要取决于连接参数、睡眠配置、事件耗时、中断耗时和内存配置。
RF 应用是另一条路，直接使用 2.4GHz RF PHY，不走标准 BLE 协议。
```
